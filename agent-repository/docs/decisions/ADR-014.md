# ADR-014: Run, attempt, and child-run identity

- **Decision owner:** project_architect
- **Decision date:** 2026-08-24
- **Status:** accepted
- **Scope:** How `spoc_id`, `run_id`, `attempt_id`, `step_id`, and
  `child_run_id` relate, especially across QA rework.

## Options considered

1. Adopt the identity model in plan section 19.2 verbatim: stable
   `spoc_id`/`spoc_version`, a deterministic `execution_key`, one `run_id`
   per logical execution lifecycle, one `attempt_id` per processing
   attempt (including QA rework) under the same `run_id`, `step_id` per
   Flow step, `tool_call_id` per tool invocation, and `child_run_id` for
   delegated executions (selected).
2. Treat every QA rework as a brand-new `run_id` (the plan's original,
   pre-correction M3.8 wording).

## Decision drivers

- Plan section 17.1 flags "ambiguous attempt identity" as a critical
  finding: M3.8 originally said each rework attempt is a new run, while the
  event model implies one resumable run.
- Auditability requires one coherent lifecycle per governed work package,
  while still distinguishing technical retries from QA-driven rework.

## Selected option

Use the six-identity model of plan section 19.2 exactly: a new `run_id` is
created only when the SPOC version, material input versions, workflow
version, approval scope, or explicit operator intent changes. A QA rework
normally creates a new `attempt_id` under the same `run_id`.

## Rejected options and reason

- Option 2: fragments one logical work package's audit trail across
  multiple `run_id`s, making end-to-end traceability harder and
  contradicting the "one auditable lifecycle" goal (plan section 19.2).

## Security and compliance impact

Improves auditability: a reviewer can see every attempt of a SPOC under
one `run_id` rather than hunting across disconnected run records.

## Operational impact

`RunStateStore` and `EventLedger` schemas must carry all six identity
fields (plan section 22.2 event schema).

None.
