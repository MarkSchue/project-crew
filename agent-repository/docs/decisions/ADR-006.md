# ADR-006: Enforce branch-per-run and protected main branches

- **Decision owner:** project_architect
- **Decision date:** 2026-08-24
- **Status:** accepted
- **Scope:** Git operating model for all three repositories.

## Options considered

1. One Git branch per logical run (retained across technical retries and
   QA rework attempts), with protected `main` requiring PR review and
   passing CI (selected, plan section 23.3).
2. Direct commits to `main` by automation identities.
3. One shared long-lived "agents" branch for all runs.

## Decision drivers

- Avoid merge conflicts between concurrent runs (masterplan section 25
  risk table).
- Preserve a clean audit trail per run (masterplan principle 7).
- Prevent unreviewed changes reaching the protected branch.

## Selected option

Every run operates on its own branch; QA rework attempts reuse the same
run branch (plan section 19.2, 23.3) rather than starting a new one.
`main` requires PR review, passing status checks, and disallows direct
push and force-push for automation identities (masterplan M0.4).

## Rejected options and reason

- Option 2: removes the review gate entirely; unacceptable given the
  human-approval-first design (masterplan principle 9).
- Option 3: reintroduces the exact merge-conflict and accountability
  problem branch-per-run was designed to solve.

## Security and compliance impact

Prevents unreviewed automated changes from reaching production-facing
branches; required status checks include OKF/SPOC schema and
cross-reference validation (plan M1.9).

## Operational impact

Requires a stale-workspace / rebase-conflict handling procedure (plan
section 23.3) and generated-index rebuild after integration.

## Cost impact category

None.

## Portability impact

None — standard Git branch protection, portable across GitHub/GitLab/Azure
DevOps.

## Revisit trigger

None anticipated.

## Supersedes / superseded by

None.
