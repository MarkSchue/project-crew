# ADR-023: Web UI framework choice

- **Decision owner:** project_architect
- **Decision date:** 2026-08-26
- **Status:** accepted
- **Scope:** The Phase 9 web UI (project overview, SPOC editor, run and
  approval views, knowledge-graph view, document viewer, and the
  persistent Project Manager chat panel).

## Options considered

1. Static, dependency-free frontend (plain HTML/CSS/vanilla JS, no build
   step) served by the FastAPI control plane, with client-side validation
   against the schema fetched from the backend (selected).
2. A compiled SPA framework (React/Vite, SvelteKit, etc.) with an npm
   toolchain.
3. Server-rendered templates (Jinja) with minimal client JS.

## Decision drivers

- "Artifacts remain usable without the platform" and "no proprietary UI
  dependency" (masterplan section 2.2, ADR-002) favor the simplest
  possible client.
- The SPOC editor must validate against the *same* schema as the backend
  (M9.4 DoD) — satisfied by fetching `spoc.schema.json` from the API, not
  by vendoring a copy that could drift.
- A build step and npm dependency tree add supply-chain surface and
  complexity with no benefit for a vertical-slice UI that is a client of
  the same API.

## Selected option

A single-page, hash-routed static app under `agent-repository/web/`,
served by the control plane, using only the browser's built-in APIs. The
SPOC editor fetches `spoc.schema.json` from `GET /api/v1/schemas/...` and
validates with a small, focused JSON-Schema-subset validator
(`web/js/okf-validator.js`). All data comes from the Phase 6/9 REST API;
the UI never bypasses policy or the graph.

## Rejected options and reason

- Option 2: introduces a build/supply-chain dependency disproportionate to
  the vertical-slice scope; revisit only if interactive graph editing
  needs a component library.
- Option 3: server-side rendering re-couples the UI to a server template
  engine without removing the need for client-side graph/chat
  interactivity.

## Security and compliance impact

Client-side validation is a UX convenience, never a security boundary —
the backend re-validates on every mutating call. The chat panel is
classification-aware through the M9.3 query flow.

## Operational impact

No build pipeline; static files are served by the same FastAPI process,
so the UI is always the client of the same API and cannot drift from it.

## Revisit trigger

If M9.5/M9.6 graph interaction or component needs exceed what vanilla JS
maintains comfortably, revisit a compiled framework.
