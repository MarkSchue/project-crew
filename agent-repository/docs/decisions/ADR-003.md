# ADR-003: Use an operational database for concurrency and resumability

- **Decision owner:** project_architect
- **Decision date:** 2026-08-24
- **Status:** accepted
- **Scope:** Operational state storage (queues, leases, run state, indexes).

## Options considered

1. SQLite for local development, PostgreSQL for shared deployment,
   accessed through the same application ports (selected).
2. SQLite everywhere, including shared deployment.
3. A NoSQL document store (e.g. MongoDB) for run state.

## Decision drivers

- Local-first development must work with zero external infrastructure
  (inception decision: local-only first).
- Shared deployment needs real concurrent access, transactions, and an
  outbox pattern (plan section 22.1).
- Avoid inventing a bespoke storage engine.

## Selected option

SQLite backs `RunStateStore` and related ports in local development;
PostgreSQL backs the same ports in shared deployment (masterplan section
26). Both are accessed exclusively through the ports defined in plan
section 20.1, so the runtime and execution-plane code do not depend on a
specific database.

## Rejected options and reason

- Option 2: SQLite does not provide adequate concurrent-writer behavior
  for a multi-worker shared deployment (plan section 18 ADR-017 queue
  discussion).
- Option 3: adds a second query paradigm without a corresponding benefit;
  relational transactions are a better fit for the outbox/event-ledger
  pattern (plan section 22.1).

## Security and compliance impact

Operational database never becomes a second copy of confidential project
narrative content; it stores references, status, and redacted event
payloads (plan section 19.5).

## Operational impact

Requires a migration strategy (`agent_platform/migrations/`, plan M1.7)
compatible with both SQLite and PostgreSQL.

## Cost impact category

Low for local dev (no cost); low-medium for shared deployment (managed
PostgreSQL instance).

## Portability impact

Medium — abstracted behind `RunStateStore`/`EventLedger` ports so the
concrete database can change without touching Flow or application code.

## Revisit trigger

Throughput or availability requirements exceed what PostgreSQL can serve
directly (would trigger a dedicated queue/cache layer, see ADR-017).

## Supersedes / superseded by

None.
