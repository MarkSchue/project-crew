# ADR-017: Queue and worker platform

- **Decision owner:** project_architect
- **Decision date:** 2026-08-24
- **Status:** accepted
- **Scope:** Selecting an existing queue/workflow technology; a custom
  broker implementation is explicitly out of scope.

## Options considered

1. Local dev: a polling queue table inside SQLite (no separate broker).
   Shared deployment: PostgreSQL-native queueing via a transactional queue
   table plus `LISTEN`/`NOTIFY` for low-latency wake-up (selected).
2. A dedicated message broker (e.g. Redis Streams, RabbitMQ) from day one.
3. Write a custom in-house broker/queue implementation.

## Decision drivers

- Plan section 17.1 explicitly calls out "select a concrete worker/queue
  mechanism through ADR; do not write a custom broker" (M6.3).
- Local-first MVP should avoid a new infrastructure dependency
  (inception decision).
- Needs to integrate transactionally with the event outbox (ADR-013).

## Selected option

Use the already-selected operational database as the queue substrate: a
transactional queue/lease table for both SQLite (local) and PostgreSQL
(shared), with PostgreSQL `LISTEN`/`NOTIFY` used in shared deployment to
avoid busy-polling. No new message-broker infrastructure is introduced for
the MVP.

## Rejected options and reason

- Option 2: adds operational infrastructure (deployment, monitoring,
  failure modes) that the DB-native approach avoids, without a
  demonstrated throughput need.
- Option 3: explicitly rejected by plan section 17.1 finding M6.3
  ("do not write a custom broker").

## Security and compliance impact

None directly; queue rows carry only references (run/attempt IDs), not
confidential payloads.

## Operational impact

Requires lease/heartbeat semantics for worker crash recovery (masterplan
section 19: retries, dead-letter, cancellation).

## Cost impact category

Low — reuses the already-provisioned database; no new managed service.

## Portability impact

Medium — the queue is an application-level abstraction over the DB; a
future migration to Redis/RabbitMQ/SQS is possible without touching
Flow/application code, gated behind a `ToolExecutor`/worker-dispatch port.

## Revisit trigger

Throughput, multi-region, or priority-queueing requirements exceed what a
DB-native queue can serve; revisit jointly with ADR-003.
