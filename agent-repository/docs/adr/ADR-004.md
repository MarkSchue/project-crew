# ADR-004: Separate control plane and execution plane

- **Decision owner:** project_architect
- **Decision date:** 2026-08-24
- **Status:** accepted
- **Scope:** Process/privilege boundary between registry/policy/matching
  and CrewAI Flow execution.

## Options considered

1. Two logically and procedurally separated planes: control plane
   (registry, policy, matcher, model router, approvals, run coordination)
   and execution plane (isolated worker running the resolved manifest)
   (selected).
2. A single monolithic process performing both registry management and
   agent execution.

## Decision drivers

- Reduce accidental privilege escalation (masterplan section 3.1).
- Simplify testing of matching/policy logic independent of LLM execution.
- Allow the execution worker to run with a minimal, manifest-scoped view
   of the repository rather than full registry access (masterplan section
   28 item 8).

## Selected option

Control plane resolves and compiles an immutable run manifest; the
execution plane loads only that manifest and executes the CrewAI Flow. The
execution plane never mutates registry or governance policy directly
(masterplan section 6.2).

## Rejected options and reason

- Option 2: mixes registry mutation, policy evaluation, and LLM execution
  in one trust boundary, which was the primary defect identified in the
  original single-process design (masterplan section 3.1).

## Security and compliance impact

Directly reduces blast radius of a compromised or misbehaving execution
worker: it cannot alter agent definitions, capability catalogs, or policy.

## Operational impact

Requires a manifest-passing boundary (`spoc_compiler.py` output) between
the two planes; adds one explicit compile step before every run.
