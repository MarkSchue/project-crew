# ADR-020: Deterministic testing versus agentic QA

- **Decision owner:** project_architect
- **Decision date:** 2026-08-24
- **Status:** accepted
- **Scope:** Establishing the evidence producer/reviewer separation
  between deterministic test tools and the QA agent.

## Options considered

1. Four distinct assurance layers (structural validation, deterministic
   verification, agentic review, human acceptance), where deterministic
   tools execute tests/scans/policy checks and produce immutable
   `TestEvidence`, and the QA agent only interprets that evidence, never
   re-executes or overrides it (selected, plan section 21.1-21.2).
2. The QA agent directly runs and interprets tests via free-form tool
   calls, with no separate deterministic executor contract.

## Decision drivers

- Plan section 17.1 flags "an AI QA agent must not be the executor of
  deterministic tests" as a critical correction.
- Masterplan section 29 acceptance criteria requires QA validation against
  acceptance criteria and linked test cases to be auditable and
  non-fabricable.

## Selected option

A `TestCase` declares its `executor` (tool id/version, command profile,
timeout, network access) per plan section 21.2; the tool runner executes
in a sandbox and writes a signed/hashed `TestEvidence` record that the QA
agent receives alongside the acceptance criteria and produced artifact,
but cannot alter. Qualitative tests may use
`executor.type: agentic_review` with a versioned rubric and human
escalation threshold, but this is still evidence-producing, reviewed
input to acceptance — not a substitute for deterministic checks where
those exist.

## Rejected options and reason

- Option 2: allows an LLM to both produce and interpret its own evidence,
  which plan section 17.1 identifies as "QA-agent overreach" and a
  critical finding.

## Security and compliance impact

Prevents a compromised or hallucinating QA agent from fabricating a
passing result; deterministic evidence is immutable once produced.

## Operational impact

Requires a `ToolExecutor` port and sandboxed runner (plan section 20.1)
before the QA gate (M3.8) can be considered complete.
