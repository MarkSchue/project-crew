# ADR-018: Artifact storage

- **Decision owner:** project_architect
- **Decision date:** 2026-08-24
- **Status:** accepted
- **Scope:** Git size threshold, object-storage mode, content-addressing,
  malware scanning, and retention for binary/large artifacts.

## Options considered

1. Files at or below 5 MB are committed directly to Git; larger or binary
   artifacts are stored in an object store (local disk in development,
   S3-compatible storage in shared deployment), content-addressed by
   `sha256`, and referenced from Markdown via an `artifact_descriptor`
   OKF-adjacent record (plan section 23.2) (selected).
2. Store all artifacts, regardless of size, directly in Git (with Git
   LFS for large files).
3. Store all artifacts in the object store, never in Git.

## Decision drivers

- Plan section 17.1 flags missing binary-storage thresholds/malware
  scanning/retention as a high finding.
- Git performance degrades with many large binary commits.
- Provenance must still be traceable from an OKF Markdown artifact
  descriptor even for non-Markdown content (masterplan section 9.5).

## Selected option

- Git size threshold: 5 MB per file (configurable).
- Below threshold: committed to Git directly.
- At or above threshold: stored in the object store, referenced via
  `artifact_descriptor` (plan section 23.2 schema) with `content_hash`,
  `size_bytes`, `storage.object_key`, and `malware_scan` status.
- Malware scanning: a scan hook is required before an artifact descriptor
  can be marked `clean`; the concrete scanner is selected when object
  storage is provisioned (tracked as a follow-up decision, not blocking
  the MVP schema).
- Retention: per the classification-based rules in
  `DEC-INCEPTION-001` ("retention rules" section).

## Rejected options and reason

- Option 2 (Git LFS for everything): adds an LFS dependency and does not
  by itself solve malware scanning or retention policy.
- Option 3 (nothing in Git): breaks the "Git is authoritative" principle
  (ADR-002) for artifacts that are small enough to review as diffs.

## Security and compliance impact

Malware-scan status is a required field before an artifact is considered
usable; unset/failed scans block acceptance.

## Operational impact

Requires an object-store adapter (`ObjectStore` port, plan section 20.1)
before Phase 6 shared deployment; local development may use a local-disk
implementation of the same port.

## Cost impact category

Low for local dev; low-medium for shared deployment (object storage
costs scale with artifact volume).

## Portability impact

High (positive) — `ObjectStore` is an application port; the concrete
backend (local disk, S3, Azure Blob) is swappable.

## Revisit trigger

Threshold proves too low/high in practice, or a specific compliance
requirement mandates a particular scanner/vendor.
