# ADR-022: Build-versus-reuse decision

- **Decision owner:** project_architect
- **Decision date:** 2026-08-24
- **Status:** accepted
- **Scope:** Fit-gap outcome for CrewAI AMP, an internal Agent Factory (if
  accessible), APM concepts, LangGraph/Temporal-style durable
  orchestration, coding-agent backends, and existing PM systems. No
  adoption is implied by evaluating an option; each is judged against
  this project's requirements.

## Options considered / evaluated

1. **CrewAI AMP** (managed CrewAI offering): evaluated as a potential
   hosting/observability layer. Not adopted for MVP — introduces a vendor
   dependency and hosted-data-residency questions before the local-first
   MVP needs them (inception decision: local-only first). Revisit at
   Phase 6 shared deployment.
2. **Internal "Agent Factory" platform**: not accessible/does not exist
   for this project; no evaluation possible. Not adopted.
3. **APM (agent/application performance management) concepts**: general
   observability ideas (traces, metrics) are adopted conceptually via
   OpenTelemetry (masterplan section 26), not as a specific vendor product.
4. **LangGraph / Temporal-style durable orchestration**: evaluated as an
   alternative execution substrate. Not adopted for MVP; see ADR-011
   (CrewAI Flow persistence is sufficient for now; durable-workflow engine
   remains a documented migration path).
5. **Existing coding-agent backends** (e.g. third-party autonomous coding
   agents) as a substitute for the CrewAI execution plane: not adopted —
   this project's governance model (manifest compilation, policy gating,
   QA rework loop) is a first-class requirement that generic coding-agent
   backends do not provide out of the box.
6. **Existing PM systems** (Jira, Azure Boards, Linear) as the requirements
   system of record: not adopted for MVP per `DEC-INCEPTION-001`
   ("Which project-management system, if any, is synchronized?" -> none
   for MVP); OKF Markdown remains the system of record. Integration is a
   deferred Phase 7+ capability.

## Decision drivers

- Avoid adopting new vendor/infrastructure dependencies before the
  local-first MVP demonstrates the governance model works (masterplan
  section 32 final recommendation: "start with a narrow, governed vertical
  slice").
- Preserve the durable asset described in masterplan section 32: versioned
  contracts, reusable capability definitions, controlled tools, project
  knowledge, evaluations, and auditable execution — not a specific vendor
  product.

## Selected option

Build on CrewAI (ADR-001) plus a plain Python control plane; do not adopt
CrewAI AMP, a separate durable-workflow engine, third-party coding-agent
backends, or external PM system synchronization for the MVP. Re-evaluate
each option independently once the corresponding revisit trigger (listed
per option above, or in the related ADR) fires.

## Rejected options and reason

See per-option rationale above; the common theme is added operational or
vendor dependency without a demonstrated MVP-blocking need.

## Security and compliance impact

Avoiding external SaaS dependencies for the MVP keeps confidential
project data under direct local/on-prem control (aligned with
`DEC-INCEPTION-001` data-classification answer).

## Operational impact

None additional beyond what ADR-001, ADR-011, and ADR-017 already
establish.

## Cost impact category

Low — no new vendor contracts for the MVP.

## Portability impact

High (positive) — avoids lock-in to a specific vendor platform before the
architecture has proven itself.

## Revisit trigger

Phase 6 shared deployment planning should re-evaluate CrewAI AMP and
managed hosting options; ADR-011's exit criteria governs the durable-
workflow-engine question; `DEC-INCEPTION-001`'s PM-system answer should be
revisited if multi-team adoption requires external PM integration.
