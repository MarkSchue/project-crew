# ADR-016: Policy engine

- **Decision owner:** project_architect
- **Decision date:** 2026-08-24
- **Status:** accepted
- **Scope:** Policy engine library/service and policy bundle format;
  fail-closed vs. local-development behavior.

## Options considered

1. An embedded Python rule-based `PolicyDecisionPoint` implementation for
   the MVP, versioned as a "policy bundle" (a directory of declarative
   YAML rule files under `policies/`), fully fail-closed, wrapped behind
   the `PolicyDecisionPoint` port so it can be swapped for an external
   engine later (selected).
2. Open Policy Agent (OPA) / Rego as an external policy service from day
   one.
3. No dedicated policy engine; authorization checks hand-written per tool.

## Decision drivers

- Local-first MVP should minimize new infrastructure (inception decision).
- "Policies override prompts" (masterplan principle 8) requires a single,
  consistently-applied decision point rather than scattered checks.
- Must fail closed on policy engine error (ADR-007).

## Selected option

Implement `PolicyDecisionPoint` as an in-process Python component that
loads versioned YAML policy bundles from `agent-repository/policies/` and
evaluates access/execution/model/data/approval rules deterministically.
Every decision records a `policy_decision_id` and the bundle version (plan
section 17.3 change map, M5.1 row). On any internal error, evaluation
returns `deny` (fail-closed). Local development uses an explicitly
labeled, non-production-permissive default bundle so onboarding does not
require a full rule set on day one.

## Rejected options and reason

- Option 2 (OPA now): adds an external service dependency before the
  MVP has demonstrated the rule complexity actually needs it; the port
  abstraction makes this migration low-cost later.
- Option 3: reproduces the "scattered ad hoc checks" problem ADR-007 was
  designed to close.

## Security and compliance impact

Fail-closed behavior is the default; any policy engine internal error
blocks the action rather than allowing it.

## Operational impact

Policy bundles are versioned and validated in CI like any other governed
artifact (ADR-010).

## Cost impact category

None — no new infrastructure for the MVP.

## Portability impact

High (positive) — `PolicyDecisionPoint` is an application port; migrating
to OPA/Rego later requires only a new adapter.

## Revisit trigger

Rule complexity, multi-tenant policy requirements, or a need for policy
authored/managed outside the Python codebase (e.g. by a dedicated
compliance team) would justify migrating to OPA.

None.
