# ADR-008: Keep global and project knowledge separate

- **Decision owner:** project_architect
- **Decision date:** 2026-08-24
- **Status:** accepted
- **Scope:** Knowledge storage boundaries across the three repositories.

## Options considered

1. Strict separation: `agent-repository/public_knowledge` (global,
   project-independent) vs. `active-project-repo/public` and
   `private/<agent_id>` (project-specific, and agent-confidential)
   (selected, masterplan section 7).
2. A single shared knowledge base for all projects and agents.
3. Per-project copies of all agent knowledge, duplicated per project.

## Decision drivers

- Prevent project-confidential data leaking into globally reusable agent
  knowledge (masterplan section 2.2, section 25 risk: knowledge
  contamination).
- Allow agents and tools to be reused across projects without
  cross-project data exposure.
- Avoid unbounded duplication and drift of shared knowledge.

## Selected option

Global, project-independent knowledge lives only in `agent-repository`.
Project-specific public knowledge lives in `active-project-repo/public`.
Agent-confidential working data lives in per-agent `private/<agent_id>`
scopes, isolated per project. Promotion of project knowledge to global
knowledge is a curated, human-reviewed workflow, never automatic
(masterplan section 28 item 10).

## Rejected options and reason

- Option 2: directly causes the "knowledge contamination" risk (masterplan
  section 25) — confidential or incorrect project-specific content could
  reach other projects.
- Option 3: duplication drifts and cannot be kept consistent; defeats the
  purpose of a reusable agent repository.

## Security and compliance impact

Enforced by the same path-security kernel and classification rules as
project artifacts (ADR-007); no automatic promotion path exists.

## Operational impact

Requires an explicit "promote to public_knowledge" change-managed
workflow (future milestone, not yet scheduled — tracked as a backlog item
under Epic W7/W8).
